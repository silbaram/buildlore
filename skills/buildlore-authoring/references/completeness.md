# Completeness authoring

This is the standard new Wiki authoring workflow. Consult the installed `buildlore/schemas/project-knowledge-completeness.schema.json` and `buildlore/schemas/project-knowledge-workflow.schema.json` for input shapes. A v5 purpose (`authoringMode: completeness-v2`) starts a v6 run with bounded inventory correction and portable review evidence. Explicit v4 purposes and saved v4/v5 runs retain the original completeness-v1 protocol and terminal behavior. Never relabel an old run to resume it under the new policy.

- Read `compile hierarchy status --project <id> --run <id> --role <role> --json`. Roles are `author`, `completeness-reviewer` and `source-reviewer`; show each reviewer only its role view.
- `material.exchange` is a `knowledge-completeness-exchange-view.v2` projection. Missing source arrays are not empty or reviewed. The original `exchangeDigest`, snapshot metadata, questions and material counts identify the full frozen inputs. For question-specific inspection use `knowledge-authoring-inspection-request.v1` with `sources`, `find`, `read` or `coverage`. For whole source records and historical facts/evidence, use `knowledge-completeness-material-request.v1` with `projectId`, `collection` (`sources`, `evidence`, `baseline-records`, `baseline-evidence`), optional `cursor`, `limit` (1–50) and `maxBytes` (8192–1048576). Pass the request through `compile hierarchy inspect --project <id> --run <id> --input <file> --expect-exchange <digest> --json`. Follow returned cursors; for `item-too-large`, retry the same cursor at `minimumRequiredBytes` if within the maximum. Never skip the item or infer its contents.
- Every `compile hierarchy completeness <action>` write takes `--project`, `--run`, `--input` and `--expect-stage` copied from that role's current `stageViewDigest`.
- Commit the blind reviewer's `shadow` inventory before the author's `inventory`. An independent `inventory-review` accepts or identifies missing items; use `reconcile` only when requested by the actual stage. Preserve all review dispositions.
- Before committing either inventory, ask whether each broad guarantee can fail under a documented condition. Compare summary claims with detailed limits, exceptions and recovery paths in the selected sources. Preserve the supported qualification and its evidence in the item itself; waiting until prose leaves an incorrect frozen obligation. During union review, independently re-open the relevant evidence and check the proposed guarantees and conditions before accepting them. For completeness-v2, record later inventory defects and use the explicit correction stage; a corrected paragraph alone cannot repair the frozen inventory.
- The coordinator must use separate host-agent contexts for author, omission reviewer and support reviewer. Each source-first inventory is independently produced from the same selected sources and questions. The author must not see the shadow inventory before committing its own. Keep actual agent execution references in local evaluation records. Do not simulate independence by changing a string. If a role cannot run, report that review as pending.
- Submit prose and its exact inventory-to-claim mapping through `submit`. Then obtain `review` from the completeness reviewer and `source-review` from the source reviewer. Coverage alone is not source support or approval.
- If correction is admitted, `correct` uses the fixed accepted inventory and the returned correction binding. Do not silently replace the inventory or erase earlier review rounds. When the workflow disallows another correction, report the terminal failure.
- Check current operation against old operation even when both are documented, and look for important unchanged material absent from the reused draft. Review question-level omissions outside the accepted list. A correctable inventory defect requests `correct-inventory`; do not fabricate a passing review or silently restart until a result passes. Actual missing sources and exhausted correction budgets remain blocking.
- `compile hierarchy finalize` uses the final review input and returned review/stage binding appropriate to the run. Read the emitted status before choosing flags; older non-completeness runs use different schemas and must retain their original protocol.
- A finalized completeness result still needs explicit human approval and activation. Never treat passed coverage as permission to activate or publish.
- New generations persist the inventories, mappings and review attempts with exact source/proposal bindings. Finalization, history admission, activation and reads replay this evidence. `completenessAssessment` distinguishes `pending`, `failed`, `verified` and `legacy-local-review`; basic runs report `unassessed`. Verified refers to the declared selected scope and recorded judgments, not a guarantee that every relevant fact was found.

## Inventory correction in completeness-v2

The normal path is source → independent inventories → review → author correction when needed → independent re-review → prose → two reviews → finalization. AI agents write and judge the content; code enforces ordering, immutable history, exact bindings and the limit of two inventory corrections total per run.

1. On `awaiting-inventory-correction`, the author reads `material.inventoryCorrectionCause`, `requiredCorrectionTargets` and the recorded defects. Submit `knowledge-completeness-inventory-correction.v1` through `correct-inventory`: copy the exchange binding, set `causeReviewDigest`, provide the complete corrected `authorInventory`, and give an explicit `resolutionId`, target, replacement author item IDs (empty only for a justified removal), and rationale for every defect and changed/removed author item. Never treat an unsourced current run status as a durable project fact.
2. Preserve previously required content. Any exclusion or substantive replacement needs an explicit item resolution and independent judgment. Declaring a different proposition a duplicate does not preserve the original. The original blind inventory and every prior cycle stay recorded; do not regenerate shadow to hide a finding.
3. The independent omission reviewer reopens the relevant selected evidence, reviews the entire original-shadow/corrected-author union, and submits `knowledge-completeness-inventory-correction-review.v1` through `inventory-review`. Include the ordinary full inventory `review`, the exact correction digest and one `resolved`/`unresolved` verdict with rationale for every resolution in input order. Use `not-required` with evidence and rationale for an unsupported original shadow item explicitly resolved by this correction. Follow `reconcile` only if the resulting stage requests it.
4. After prose has begun, finish both reviews before deciding correction. The cause is their combined review-round digest. Inventory correction clears the live accepted list, prose, mapping and reviews; obtain a fresh accepted list, write and map prose, and request both independent reviews again.
5. Both `review` and `source-review` in v2 use `knowledge-completeness-review-submission.v1`. Copy the exchange binding plus that reviewer's `material.reviewSubmissionBinding`, nest the ordinary review under `review`, and compute `submissionDigest`. This binds the actual review to its correction cycle, accepted list, proposal and mapping, including when text is unchanged. Do not repackage an old verdict as a new review.
6. `correct` is still the single prose-only correction within an accepted inventory cycle. It does not replace `correct-inventory`. Two inventory corrections are the run-wide limit. Source gaps, source drift, invalid bindings, security failures and size limits are still blocking. Preserve the failure record and report remaining work when the limit is reached.

Use canonical JSON and the documented SHA-256 digest rules for all artifacts; consult the installed schema for exact closed keys. Prior failed runs stay historical. Starting an explicitly requested new v2 run is separate from resuming them. Finalization remains separate from human approval and activation.
