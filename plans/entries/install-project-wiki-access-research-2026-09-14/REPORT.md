# BuildLore 설치와 프로젝트별 중앙 Wiki 접근 개선 방향

조사일: 2026-09-14. 공식 문서·공개 저장소와 현재 BuildLore 작업 트리를 비교했다. 비교 제품을 설치하거나 에이전트 사용 성공률을 벤치마크하지 않았다. 아래 새 명령과 설정은 구현 제안이다. 현재 사용할 수 있는 명령으로 해석하지 않는다.

**권장 방향은 ‘한 번 설치 → PC의 Git 지식 허브 연결 → 프로젝트별 읽기 연결 → 현재 프로젝트에서 CLI 또는 MCP로 조회’다.** 중앙 지식 저장소와 프로젝트별 조회 연결을 분리하고, 기존 BuildLore 조회 서비스를 양쪽 인터페이스가 공유한다. 각 소스 프로젝트에 BuildLore 소스를 복제하거나 위키 전체를 복사하는 과정은 필요 없게 만든다.

사용자는 중앙화 형태 질문의 1번인 ‘내 PC의 여러 프로젝트에서 공유’를 후속 입력 ‘1’로 선택했다. 이번 개선의 기본 구성은 한 PC의 여러 소스 체크아웃이 하나의 로컬 지식 허브를 공유하는 방식으로 확정한다. 다른 PC의 Git 동기화는 확장 가능한 후속 시나리오이며, 원격 웹 AI의 직접 연결과 HTTP 배포·인증은 이번 기본 범위에 포함하지 않는다.

**비교 프로젝트에서 확인한 해결 방식**

| 프로젝트 | 설치·연결 방식 | 지식·프로젝트 선택 | BuildLore에 적용할 점 |
|---|---|---|---|
| Basic Memory | Homebrew 또는 uv로 설치하고 로컬 MCP 실행 명령을 에이전트에 등록 | 사용자 설정에 프로젝트와 문서 경로를 등록하고 MCP 프로세스의 프로젝트 범위를 고정 가능 | 프로그램 설치와 지식 위치를 분리하고 프로젝트마다 범위가 고정된 연결 제공 |
| Serena | 배포 패키지 설치 후 초기화, 클라이언트가 stdio 프로세스 실행 | 명시적 프로젝트 또는 cwd부터 가까운 프로젝트 경계 탐색 | 작업 폴더 중심의 사용 경험, 세션별 프로젝트 고정 |
| Context7 | setup 명령으로 CLI+Skills 또는 MCP 연결을 구성 | 안정적인 library ID로 문서 선택 | 설치·도구 등록·사용 지침을 함께 제공하고 CLI와 MCP를 모두 유지 |
| QMD | npm/Bun 전역 설치, CLI와 MCP 및 SDK 제공 | 전역 collection 레지스트리에 문서 경로 등록, 어느 cwd에서도 collection 지정 검색 | cwd와 지식 위치를 분리하고 공통 SDK를 통한 일관된 조회 제공 |
| DeepWiki | 원격 MCP URL 등록으로 공개 저장소 위키 접근 | GitHub 저장소 단위로 목차·내용·질문 도구 제공 | 작은 읽기 도구 집합과 간단한 연결 경험 참고 |

Basic Memory의 로컬 시작 문서는 설치, 클라이언트 설정, 도구 목록 확인을 연속된 과정으로 안내한다. 설정 문서는 로컬 프로젝트 경로 매핑과 `BASIC_MEMORY_MCP_PROJECT`의 프로세스·세션 단위 제약을 구분한다. BuildLore가 참고할 것은 경로 매핑과 범위 고정이다. 기본 프로젝트로 자동 fallback하거나 임베딩을 초기 실행에 자동 생성하는 정책은 그대로 채택하지 않는다. [로컬 시작](https://docs.basicmemory.com/start-here/quickstart-local), [설정](https://docs.basicmemory.com/reference/configuration)

Serena는 설치된 배포판을 권장하며, `--project-from-cwd`는 상위 디렉터리를 탐색하되 가장 가까운 프로젝트/Git 경계를 선택한다. 또한 한 인스턴스의 활성 프로젝트가 하나이므로 서로 다른 프로젝트의 에이전트는 각자 stdio 인스턴스를 쓰는 방식을 권한다. BuildLore에는 폴더 기반의 명시적 연결 검색과 세션 범위 고정을 적용할 수 있다. [설치](https://oraios.github.io/serena/02-usage/010_installation.html), [실행과 프로젝트 선택](https://oraios.github.io/serena/02-usage/020_running.html)

Context7의 현재 setup은 CLI+Skills와 MCP를 모두 제공한다. CLI에는 라이브러리 찾기와 문서 조회가 있고, setup이 사용 지침도 구성한다. ‘MCP만 있어야 AI가 문서를 읽는다’는 설계가 아니라 사용 환경에 따라 두 진입점을 제공하는 사례다. BuildLore도 연결 설정과 언제·어떻게 위키를 읽을지 안내를 함께 제공해야 한다. [공식 저장소](https://github.com/upstash/context7)

QMD는 전역 collection 경로를 등록하고 어느 디렉터리에서도 collection을 지정해 검색한다. 기본 검색은 여러 collection을 포함할 수 있으므로 이 동작을 BuildLore의 프로젝트 격리로 간주할 수는 없다. QMD의 SDK 중심 구성과 명시적 collection 선택을 참고하되, BuildLore는 한 프로젝트의 데이터를 로드하는 단계부터 범위를 제한해야 한다. [공식 저장소](https://github.com/tobi/qmd), [SDK와 MCP 구조 개편 기록](https://github.com/tobi/qmd/releases/tag/v2.0.0)

DeepWiki는 원격 URL 하나로 공개 저장소의 목차, 내용, 질문 도구를 제공한다. 사용 경험은 간단하지만 원격 서비스와 네트워크가 전제이며, 공개 서버와 비공개 저장소용 Devin 연결도 구분된다. 따라서 BuildLore의 기본 배포 구조보다는 도구 수와 연결 경험을 참고하는 사례다. [공식 MCP 문서](https://docs.devin.ai/work-with-devin/deepwiki-mcp)

**BuildLore에서 해결해야 할 실제 간격**

현재 package.json에는 CLI bin과 배포 파일 목록이 있지만 `private: true`다. README는 저장소 복제, 의존성 설치, TypeScript 빌드를 사용자 시작 경로로 안내한다. `npm run p2a:init`은 이 저장소의 개발 harness 준비이며 제품 사용자 설치에 포함할 작업이 아니다. [패키지 설정](../../../package.json#L1), [설치 안내](../../../README.ko.md#L29)

조회 서비스와 JSON 출력은 이미 있다. 부족한 것은 다른 소스 프로젝트에서 허브와 자기 project ID를 안전하게 찾아 주는 연결이다. 현재 CLI는 `runtime.cwd/knowledge`를 사용하고 허브 Git 상태를 검사한다. 로컬 레지스트리는 허브에서 project ID를 소스 체크아웃 경로에 연결하지만, 소스 프로젝트에서 허브를 찾는 사용자 수준의 연결 진입점은 없다. [CLI 경로 처리](../../../src/cli/run-cli.ts#L238), [허브 로컬 바인딩](../../../src/knowledge/local-project-registry.ts#L44)

위키 조회는 여러 기존 형식으로 분기된다. MCP가 새 조회 로직을 따로 구현하면 현재 CLI의 형식 지원과 검증이 갈라질 수 있다. 공통 읽기 서비스에 이 분기를 모으고 CLI와 MCP가 같은 결과·오류 계약을 사용하도록 구성하는 것이 적합하다. [현재 읽기 분기](../../../src/cli/run-cli.ts#L381)

**설치는 프로그램과 지식 데이터를 분리한다**

첫 배포 단계는 빌드된 공식 npm 패키지다. 현재 TypeScript/Node 구현을 재사용할 수 있어 소스 빌드 제거에 가장 직접적이다. 패키지 이름·레지스트리 소유권을 확인한 뒤 고정 버전 설치를 안내하고, 제품 소스·개발 의존성·Plan2Agent 없이 동작하는 배포물을 검증한다. npm 설치만으로 Node 런타임 요구가 없어지는 것은 아니며 Node 24 지원 조건을 명시해야 한다.

패키지를 PC에 한 번 설치한 뒤 허브를 별도 디렉터리에 만들거나 기존 허브를 등록한다. 각 소스 프로젝트에는 실행 파일, node_modules, 지식 서브모듈을 반복 설치하지 않는다. 지식 Git submodule은 허브가 소유하고 데이터는 기존 `knowledge/projects/<project-id>/` 경계를 유지한다. 다른 PC는 프로그램을 설치하고 같은 Git 지식을 자신의 허브에 연결한다.

Homebrew/winget 또는 런타임 포함 배포물은 다음 단계로 검토한다. 네이티브 의존성이 있는 현재 구성을 독립 실행 파일로 쉽게 묶을 수 있다고 가정하지 않는다. 기본 읽기 경로에서 모델 런타임과 의존성을 분리하는 방안도 검토 대상이다. 현재 Transformers는 실행 시 지연 import되지만 직접 의존성이므로 설치 무게가 제거된 것은 아니다. 실제 용량·설치 시간은 측정이 필요하다. [임베딩 런타임](../../../src/retrieval/embedding/provider.ts#L169)

설치·업데이트·연결 해제를 모두 지원하고, 업데이트는 명시적 버전으로 수행한다. MCP 시작 때마다 latest를 가져오는 구성을 기본으로 삼지 않는다. 연결 해제나 프로그램 제거가 Git 지식 파일 삭제로 이어지지 않도록 계약을 분리한다.

**프로젝트에서는 연결 정보만 선언한다**

연결 정보는 두 계층으로 나눈다. 소스 저장소가 공유하는 파일에는 지식 저장소의 이식 가능한 식별자와 project ID를 저장한다. PC별 레지스트리에는 그 지식 저장소가 체크아웃된 허브 절대 경로와 실제 연결한 소스 루트를 저장한다. 파일명은 예를 들어 `.buildlore/connection.json`을 검토할 수 있으나 아직 계약이 아니다. 이미 sources.json이 있으면 프로젝트 식별자의 일치를 검증하고, 읽기 연결을 위해 수집 범위를 새로 만들거나 바꾸지 않는다.

프로젝트 루트 또는 하위 폴더에서 명령을 실행하면 가장 가까운 Git worktree 경계 안에서 명시적 연결을 찾는다. 폴더 이름, 첫 번째 등록 프로젝트, 최근 사용 프로젝트로 추측하지 않는다. 복수 후보·식별자 불일치·다른 저장소 경계는 구체적인 연결 오류로 반환한다. 명시적으로 저장된 연결을 재사용하는 것이며 일반 전역 기본 프로젝트를 도입하는 것은 아니다.

git worktree에는 동일한 project ID를 쓰는 별도 로컬 읽기 연결을 허용하는 방향이 적합하다. 현재 쓰기용 registry가 project ID별 sourceRoot 하나를 관리하므로, 읽기 연결이 그 바인딩을 매번 교체해서는 안 된다. clone, worktree, 하위 디렉터리, 중첩 저장소, 심볼릭 링크 경계를 각자 검사해야 한다. URL 별칭이나 저장소 이동은 명시적 재연결로 해결한다.

기존의 허브 운영 명령과 `--project` 사용은 유지한다. 새로운 프로젝트 독자 경로에서만 검증된 연결의 project ID를 내부 요청에 넣는다. 실제 구현 전에는 현재 ‘프로젝트를 추론하지 않는다’는 CLI 계약과 새 연결 계약의 관계를 P2A Gate에서 명시해야 한다.

**AI 연결은 CLI+짧은 지침과 읽기 전용 MCP를 제공한다**

셸 에이전트는 현재 프로젝트에서 CLI를 호출한다. MCP 클라이언트는 시작 때 지정된 프로젝트 루트의 연결을 읽고, 그 세션을 하나의 허브·project ID에 고정한다. 전역 current-project를 전환하는 명령이나 다른 프로젝트 목록 전체를 노출하는 도구는 첫 독자 연결에 두지 않는다.

작업 폴더의 cwd를 전달하는 것이 확인된 클라이언트는 그 기능을 사용한다. GUI 클라이언트 등 cwd가 보장되지 않는 환경에는 명시적 프로젝트 루트를 넣은 PC 로컬 실행 설정을 생성한다. MCP의 서버 cwd가 언제나 소스 프로젝트일 것이라고 가정하지 않는다. 실행 파일의 실제 경로, 스키마, 등록 위치는 지원 클라이언트별로 검증하고 사용자 기존 설정을 보존해 병합한다.

MCP stdio는 클라이언트가 실행한 프로세스와 표준 입출력으로 통신한다. 세션 중에는 프로세스가 존재하지만 사용자가 별도 상시 서비스를 운영할 필요가 없다. 중앙 DB나 HTTP 서비스 없이 같은 로컬 Git 지식을 읽을 수 있다. [MCP 전송 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

기본 도구는 status, list, search, read, memory, lookup/citations 정도로 제한한다. 처음 작업을 받으면 제한된 memory를 조회하고, 부족한 항목은 search/read, 인용 전에는 lookup으로 이어지는 안내를 함께 제공한다. 전체 Wiki나 복잡한 생성·승인·게시 명령을 초기 컨텍스트에 넣지 않는다. Resources는 문서 선택 UI를 위한 추가 기능으로 검토하고, 모델의 실제 조회는 Tools에서도 가능하게 한다. [MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [MCP Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)

사용 지침은 기존 AGENTS.md/클라이언트 규칙의 사용자 내용을 보존하는 방식으로 추가한다. 제품의 짧은 읽기 안내는 제공하되, BuildLore 개발용 Plan2Agent 스킬과 관리 자산을 다른 소스 프로젝트에 설치하지 않는다. 도구 등록만으로 에이전트가 적절한 순간에 위키를 사용할 것이라고 가정하지 않는다. Basic Memory 역시 별도의 사용 지침과 Skills를 안내한다. [AI 안내 방식](https://docs.basicmemory.com/reference/ai-assistant-guide)

**범위·최신성·복구는 연결 계약에 포함한다**

프로젝트 범위는 검색 결과를 마지막에 필터링하는 수준이 아니라 데이터 로드, 커서, 페이지 ID, 근거 조회, 캐시 키에서 모두 검사한다. 응답과 커서는 프로젝트 및 generation에 결속하고 generation 변경 시 이어 읽기를 재시작하도록 안내한다. Basic Memory에는 과거 도구 범위와 background sync 범위가 다르다는 버그 보고가 있었고 이슈는 닫혀 있다. 현재 취약점 주장으로 사용하지 않으며 모든 하위 작업에 범위를 전파해야 한다는 회귀 테스트 사례로 참고한다. [이슈 #434](https://github.com/basicmachines-co/basic-memory/issues/434)

PC 간 동기화는 Git으로 수행하되 읽기는 로컬의 검증된 승인 generation을 사용한다. 조회 과정에서 pull, merge, 위키 재생성, 승인, 인덱스 재생성, 모델 다운로드를 묵시적으로 수행하지 않는다. 별도 refresh 작업이 원격 변경을 확인·반영하고, dirty 상태·충돌·submodule pin은 기존 규칙에 따라 처리한다. 단순히 submodule에서 git pull을 실행하면 허브 pin과 불일치할 수 있으므로 전용 갱신 계약이 필요하다.

status는 로컬 지식 revision, 승인 generation, 선택한 읽기 정책, 마지막 원격 확인 상태와 복구 단계를 구분한다. 원격을 확인하지 않았으면 최신이라고 주장하지 않는다. 작업 중인 소스 코드와 위키의 근거 revision이 다르면 그 한계를 알려 준다. 현재 미커밋·활성화·게시 상태의 의미를 편의 기능 때문에 바꾸지 않는다.

로컬 도구의 프로젝트 제한은 BuildLore 조회 경로의 격리다. 같은 OS 계정의 임의 셸이나 전체 지식 Git clone 접근까지 차단하는 ACL은 아니다. 서로 다른 사용자의 지식 접근 권한까지 분리해야 한다면 저장소/OS 권한 또는 별도 인증 계층 설계가 필요하다. 파일 접근이 프로젝트 폴더로 제한된 AI 환경에는 허브의 허용된 mount/접근 설정 또는 그 위치를 읽을 수 있는 MCP 실행 환경이 필요하며, MCP 등록만으로 OS 권한이 생기지 않는다.

**제안 사용자 흐름 — 아직 구현되지 않은 예시**

공식 배포 패키지를 설치한 다음 다음과 같은 흐름을 제공한다. 명령 이름·옵션은 Gate에서 확정한다.

```sh
# PC에서 최초 한 번: 허브 생성/등록과 지식 Git 연결
buildlore setup --hub ~/BuildLore --knowledge-repo <knowledge-git-url>

# 이미 등록된 프로젝트 a의 소스 루트에서 한 번: 읽기 연결과 AI 안내 구성
buildlore connect --hub ~/BuildLore --project a

# 같은 프로젝트의 이후 세션: 허브로 이동하거나 project ID를 반복할 필요 없음
buildlore wiki memory --task "인증 설계와 주의사항" --progressive --json
buildlore wiki read --page architecture --json
buildlore doctor --json

# MCP를 선택한 클라이언트가 실행할 명령 예시
buildlore mcp --project-dir <absolute-source-root> --read-only
```

connect는 허브에 없는 project ID를 조용히 생성하지 않는다. 새 프로젝트 등록·소스 수집 설정과 기존 Wiki 읽기 연결은 구분한다. Wiki가 없으면 연결은 성공했지만 읽을 승인 Wiki가 아직 없다는 상태와 필요한 운영 단계를 보여 준다. GUI 설정을 적용한 뒤 재시작 또는 도구 reload가 필요한 경우 완료 메시지에 표시한다.

**대안 판단**

| 대안 | 장점 | 이번 방향과의 적합성 |
|---|---|---|
| 기존 CLI와 경로 안내만 보완 | 변경이 작고 빠름 | 단기 우회로는 가능하나 새 프로젝트마다 연결을 반복 설명해야 함 |
| 전역 설치 + 명시적 프로젝트 연결 + CLI/stdio MCP | 기존 Git 구조 재사용, 셸·MCP 모두 지원, 오프라인 읽기 | 권장 기본안 |
| 프로젝트마다 위키 복사·symlink | 파일 읽기 도구로 접근 가능 | 복사본 최신성·버전 혼합·경계 및 OS 호환 문제가 있어 기본안으로 부적합 |
| 중앙 HTTP MCP 서비스 | 원격·웹 AI에 유리하고 서버 자원 공유 가능 | 네트워크·인증·운영이 필요한 별도 범위. 원격 연결 요구가 확인될 때 확장 |
| 외부 메모리 제품으로 교체 | 해당 제품의 연결 기능 활용 | BuildLore의 승인·provenance·Git 계약을 이식해야 하므로 이번 사용성 개선보다 범위가 큼 |

**실행 우선순위와 완료 판단**

1. 설치·연결 기반: 실제 배포 tarball을 깨끗한 소비자 환경에 설치하고, 별도 허브와 프로젝트 연결을 만든 뒤 프로젝트 안에서 첫 Wiki를 읽는다. 제품 소스 빌드와 P2A 자산을 요구하지 않는 것을 검증한다.
2. AI 독자 경로: 공통 읽기 서비스, 명령별 도움말과 복구 오류, CLI 사용 지침, 프로젝트에 고정된 stdio MCP 및 지원 클라이언트별 연결 설정을 제공한다. CLI와 MCP가 동일한 승인 결과를 반환하는지 확인한다.
3. 반복 사용: 다른 PC의 경로 재연결, clone/worktree, 명시적 Git 갱신과 revision 안내, 업데이트·연결 해제를 검증한다. 필요가 확인되면 런타임 포함 배포와 원격 MCP를 후속 범위로 검토한다.

완료 기준은 설치 명령 성공이나 도구 목록 표시만이 아니다. 서로 다른 두 실제 에이전트 클라이언트가 각기 프로젝트 a와 b에서 자기 Wiki를 발견하고, 질문에 필요한 본문과 실제 근거를 읽어 답하는 전체 흐름을 실행해야 한다. 동시 조회, 잘못된 project/page/cursor, 다른 generation, 허브 누락, 승인 Wiki 없음, dirty/pin 충돌, 오프라인, Windows 경로·공백·한글 경로를 포함한다. 읽기 중 네트워크·모델·지식 쓰기가 발생하지 않는지와 사용자 기존 설정 보존도 확인한다.

처음 설치부터 첫 유효한 본문 조회까지 걸린 시간, 수동 단계 수, 실패 후 복구 호출 수, AI가 실제 읽은 본문·근거와 누적 응답량을 기록한다. 이미 개발 환경에 있는 사람이 성공한 결과를 신규 사용자 설치 성공으로 계산하지 않는다. MCP 응답의 프로토콜 부가 크기를 기존 JSON data 예산과 별도로 측정한다.

**이번 조사 기록**

조사 entry는 p2a validate를 통과했고 p2a next는 기존 승인 작업이 진행 중이므로 새 entry를 deferred로 기록했다. 이번 요청의 결과는 조사와 방향 제시이며 제품 구현이나 기존 작업 교체가 아니다. 따라서 기존 lifecycle을 전환하지 않았다. 실제 구현에서는 위 연결 범위, 기본 프로젝트 해석, 배포 방식 및 로컬 MCP를 P2A Gate의 제품 계약에 반영한다.

현재 작업 트리에는 기존 수정이 있다. 로컬 근거 파일의 SHA-256과 조사 출처 URL은 provenance.json에 기록한다. 외부 문서의 기술·사용성 주장은 공식 문서상의 동작이며 설치 재현·성능·AI 성공률의 독립 검증 결과가 아니다. 본 보고서는 제품 코드, 지식 저장소 내용, 사용자 클라이언트 설정을 변경하지 않는다.
