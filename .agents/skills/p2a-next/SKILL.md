# Plan2Agent Next

Use the CLI result as the only decision authority. Do not infer, list, or encode project-state rules in this skill.

## Procedure

1. Run `p2a next --json --contract v2` from the target project. Pass `--project-id <id>` only when the user selected an artifact explicitly. The unqualified JSON command `p2a next --json` remains the backward-compatible `p2a.next.v1` surface; human output defaults to v2 so structured options remain visible.
2. Parse the one returned `command`, `continuation`, `reason`, `reasonCode`, and `state`. `reasonCode` is the stable schema-enumerated machine identifier and currently equals `state` for compatibility.
3. Present the result as a short development-assistant message: what P2A understood, the one material decision needed (if any), what it will do next, and why that action is recommended. Do not expose Gate names, state ids, run ids, hashes, or artifact paths unless the user asks for details or troubleshooting. Keep the exact returned command and reason available internally; never alter their machine meaning.

If the v2 result contains an `immediate` continuation, request its references once with `p2a context show --artifacts <dir> --continuation <id> --provider <provider>`. For `after_command_success`, first validate the single `p2a.execution_result.v1` result, then pass its `runId` to the same command. Do not rediscover or individually reopen packet-managed references.

## Handle the returned command

- For `kind: cli` with `requiresApproval: true`, explain the action in product language and keep the exact command internal while waiting for the user's approval. If the user explicitly approves that pending action on a later turn, execute its returned `argv` exactly once; the unchanged `requiresApproval` flag records the action's authority boundary and does not require a second approval.
- For `iteration_complete`, the user's next concrete natural-language change request is the approval and the value for the single `<change idea>` placeholder. Replace that placeholder with the verbatim request and execute the returned argv once. The CLI allocates the next iteration id; do not ask the user to invent one.
- For `entry_deferred`, explain that the new request is saved but cannot silently replace or start ahead of the current approved work. Do not execute the existing approved work item in the same turn. If the user chooses to continue the current work, rerun plain `p2a next`; after that iteration closes, resume the saved entry path reported by the action.
- For `blocked_scope_replacement_ready`, explain that the old blocked task and run evidence will stay intact while a new planning iteration starts from the last approved development contract. Execute the returned `replace-scope` argv only after explicit approval. After success, rerun `p2a next` with the same `--entry` used for this decision so scope confirmation continues from the exact request.
- For `kind: cli` with `requiresApproval: false`, run it immediately. This flag is emitted only for read-only repair inspection or the post-Gate B development, verification, and required-review loop already authorized by the approved contract. Iteration close is never part of this automatic loop.
- When the state is `relevant_verification_required`, explain that product files are unchanged: a docs-only iteration needs no product-wide verification, while a current product pass remains reusable when one exists. Run the returned `--scope relevant` action; do not offer or substitute a full product test.
- For `kind: approval` with `options`, present every structured option and wait for the user's explicit choice. For `review`, keep the iteration open and perform a read-only review of the completed diff, code, tests, and existing current-revision final verification evidence. Judge test adequacy from those sources, but do not rerun tests, builds, lint, typechecking, or other product commands merely because review was selected; `next` already routes missing or stale final evidence before offering this choice. If a finding requires code changes, replace the placeholders in the returned `action.remediation` command with the owning completed task id and a concrete finding note, run it, then run `next` to enter a new remediation run through the normal lifecycle. After a clean review, report no material issue and ask once whether to execute the returned `close` action; do not run `next` or redisplay the same menu. For `retrospective`, keep product review and close separate: report returned candidates in plain language and distinguish product verification performance from P2A workflow signals, or when there are none ask once whether the user experienced P2A delay, errors, wrong routing, or unnecessary steps. If the user reports an issue, summarize the observed fact, user impact, and suggested improvement before asking whether to continue the retrospective; if they report none, create nothing and return to the same decision. When the user explicitly continues, write the returned `action.report.path` once with only `Observed issue`, `User impact`, `Suggested improvement`, and concise evidence; do not overwrite an existing report, copy raw command output, or infer missing facts. Report approval does not authorize proposal mining. For `close`, the user's exact choice authorizes only the returned nested close command; execute it without treating a clean review or retrospective as approval.
- Proposal mining writes proposals from retrospective candidates and therefore always requires approval; never treat it as part of the autonomous close loop.
- When `state` is `flat_execution_complete`, report the returned completed result and verification summary, explain that this handoff has no iteration to close, and stop. Do not route the terminal payload back to `p2a-harness` merely because it has no approval argv.
- When a CLI action has an `after_command_success` continuation, execute its returned `argv` exactly and parse the single `p2a.execution_result.v1` JSON document. Activate the continuation only when the command exits zero, `outcome` is `succeeded`, and `runStatus` is `started`; bind the returned `runId` without parsing human output.
- For `kind: skill`, continue in this agent session with the returned `skill` and `args`. Carry over only the declared continuation context; do not re-decide the next action.
- For `gate_b_approved_needs_execution_prepare`, pass the returned `--prepare-mode` to `p2a-dev-execution`. The skill selects and records the concrete adaptive mode; do not ask the user to choose from a mode menu or approve the synthetic compatibility work item.
- For `kind: approval` without `options`, present the returned `decisionSummary` in product language and wait for the user's answer. Keep the returned artifact path and approval command internal unless the user requests details or troubleshooting. When the user explicitly approves that pending decision, replace the one exact `quotePlaceholder` argument in the returned `argv` with the verbatim user utterance and execute that argv exactly once. For `tasks_blocked`, this records the answer on the task and returns only that task to `todo`; run `next` afterward and continue the ordinary retry. If the user rejects the bounded recovery because product scope or the dependency contract must change, leave the task blocked and rerun `p2a next --idea "<replacement scope>"` or `--entry <path>`; the CLI will offer the separate approval-bound replacement transition when it is safe. If a legacy v2 payload has no `argv`, return to the owning `p2a-harness` approval procedure instead of parsing the human `display` string.

Never execute a CLI command with `requiresApproval: true` before the user explicitly approves that exact pending action. Do not reuse approval for a different action or after its state changes. If the CLI requests project selection, ask the user to choose the displayed project id and run this skill again with that id.
